# 会話の不自然さ：修正対象と実装計画

状態: **修正計画。実装は未着手。**

根拠: [23往復の診断](CONVERSATION_AUDIT_2026-11-06.md)、[全発話記録](CONVERSATION_AUDIT_TRANSCRIPT_2026-11-06.md)。以下の順で修正する。単にモデルを変更するだけでは、場面進行と履歴の不整合は解消しない。

## 1. プレイヤーの返答候補を作る処理【最優先】

**対象:** `src/lib/server/conversation-llm.ts` の `generationSchema`、`conversationReply`。呼び出し元は `src/lib/server/conversation-service.ts` の `dialogue/message`・`dialogue/action`。

**問題:** 相手の台詞と次のプレイヤー候補を同時生成し、話し手が逆転する。毎回「共感・反対・質問」を必須にして、直前の希望を否定する候補も作っている。

**変更内容:**

- 相手の台詞を確定してから、その台詞を入力に含めてプレイヤー候補を生成する関数を分ける。
- 入力に `player` と `companion` の対応を明示し、最新のプレイヤー発言・相手の返答・既存履歴を区別する。候補は「次にプレイヤー本人が送る文章」として生成する。
- 毎回の反対意見・質問を必須にしない。3候補は維持しつつ、「短く応じる／話を広げる／別の話題」など、その場に合う違いにする。その他入力も維持する。
- 話し手の取り違え、明示した希望との矛盾、未共有の体験の断定、ほぼ同じ候補を検査する。不正な候補は限定回数だけ再生成し、失敗時は安全な短い候補と自由入力へ退避する。意味の検査は完全ではないため実会話でも評価する。
- 候補生成だけが失敗しても正常な相手の返答を失わないようにする。現在の送信ID・revision・再送時の二重追加防止を維持する。

**合格例:** 「私が仕事でミスした」の後のプレイヤー候補は「聞いてくれてありがとう」「今日は別の話がしたい」などになり、「どんなミスをしたの？」と相手へ聞き返さない。「今日は静かに過ごしたい」に、人混みへ行きたいとする候補を出さない。

## 2. 相手の返答内容と記憶の扱い【最優先】

**対象:** `src/lib/server/conversation-llm.ts` の `conversationReply`、必要に応じて `src/lib/server/llm.ts` の生成入力形式。

**変更内容:**

- 返答の優先順位を「直接の質問に答える → 頼まれた会話内の行為を行う → 必要なら次の話題」にする。
- 「甘いと思ったら辛かった」は感想であり、辛いもの好きという好みの確定ではない、と区別する。
- 2〜4文固定を外し、短い返事や1文の受け止めを許可する。毎回の理由質問や感情分析を避ける。
- 「遊びを始めて」ならその場で出題する。「黙って飲みたい」なら短く応じて、気持ちの説明を求めない。
- 「確定した場面の事実」「会話で共有された事実」「これからの提案」を分ける。未設定の映画は「まだ決めていなかったね。コメディはどう？」など、提案として扱う。
- 自由会話でできる言葉遊びと、場面の移動・確定イベントを区別する。LLMが場面を勝手に変更しない制約を、会話内の遊びまで禁止する意味にしない。

**合格例:** 「Miraから始めて」に実際の第一問が返る。「映画は何だっけ？」に未確定のジャンルを記憶として断定しない。

## 3. 物語と会話の時系列【最優先】

**対象:** `src/lib/rain-story.ts` の `rainStory.cafe`・`chooseStory`・`storyContext`、`src/lib/server/conversation-service.ts` の行動処理、`src/lib/conversation.ts` の状態・メッセージ記録。

**変更内容:**

- 香り当ての「提案」を押すだけで成功・失敗まで確定する現在の遷移を廃止する。
- 提案 → 出題中 → プレイヤー回答 → 結果の段階を設け、回答前には次回デートの `plan` へ進めない。
- 出題内容・正解・誰の番か・回答・結果をサーバーで管理する。正解は回答前の公開レスポンスに含めない。
- 返答生成へは変更前の場面、選んだ行動、確定した変更後の場面と結果を明示して渡す。「提案の文章」と「完了した結果」を混同させない。
- 自由会話での「ゲームをしよう」は提案として扱い、必要なら正式なゲーム開始操作へつなげる。自由会話だけでサーバー上の結果を捏造しない。
- 結末の振り返りには実際に起きた結果だけを使い、誰が間違えたかも保持する。
- 現在の「3つの行動」表示は、物語の大きな3段階とゲーム内操作を区別して更新する。追加の操作を隠して表示と実際が食い違わないようにする。

**合格例:** 出題された香りに回答して初めて結果が決まる。その後「誰が何を間違えた？」と聞くと実際の結果と一致する。途中でページを更新しても同じ問題・同じ順番から再開する。

## 4. 画面に表示する冒頭と、LLMの履歴を一致させる【高】

**対象:** `src/components/conversation-experience.tsx` の固定の冒頭吹き出し、`src/lib/conversation.ts` の `createConversation`、`src/lib/server/conversation-service.ts` の `dialogue/start`。

**変更内容:**

- UIだけにある両者共通の挨拶を、サーバーが作るキャラクター別の冒頭メッセージに移す。
- 画面は同じメッセージ履歴を表示し、LLMにもその履歴を渡す。初期候補も冒頭の発話に対応させる。
- 再開時に挨拶を追加し直さない。既存の会話にも重複挿入しない。
- 冒頭のassistant発話を追加すると、現在の `messages.length / 2` 相当の60往復判定がずれる。UI/APIの上限判定をユーザーの送信回数基準に修正する。

**合格例:** 「さっきあなたが言っていたことだけど」に、画面に存在する冒頭を踏まえて返せる。再開しても同じ冒頭が増えず、上限は60往復のまま。

## 5. AshaとMiraの違いを行動に反映する【中】

**対象:** `src/lib/server/demo.ts` の `demoPersona`、`src/lib/server/conversation-llm.ts` の人物設定の受け渡し。

**変更内容:**

- 固定の架空キャラクターには、話題を始められる具体的な関心・その日の気分・反応例を設定する。
- Ashaは短く受け止めて観察や控えめな冗談を返す。Miraは軽い遊びを自分から一手始める。違いを敬語／タメ口だけにしない。
- 自分の好みを持ちながら相手の希望にも応じる。「落ち着いた人だから毎回静かな場所を説明する」という反復を避ける。
- この架空設定は固定キャラクターに限定し、ユーザー由来のPersonaに未承認の経歴や体験を追加しない。

**合格例:** 同じ「緊張している」「何か遊ぼう」への返事で、口調以外の反応・行動の違いが現れる。

## 6. JP/EN切り替え後の返答候補【中】

**対象:** `src/lib/conversation.ts` の `switchSuggestionLanguage`、`src/lib/server/conversation-service.ts` の取得・再開処理。

**変更内容:**

- 言語変更時の汎用固定3文を、現在の相手の発言と履歴に対応する指定言語の候補へ置き換える。
- 元の発話や過去の履歴は翻訳・上書きせず、新しい候補と以後の返答だけ変更する。
- 候補を生成している間に会話が進んだ場合は、古いrevisionの結果を反映しない。古い言語の候補も送信できない状態を維持する。

**合格例:** チャイの甘さの話でENへ切り替えても、話題が突然「二人の心地よさ」に変わらない。

## 7. 品質確認を追加する【各修正と同時】

**対象:** `tests/conversation.test.ts`、`tests/rain-story.test.ts`、`scripts/check-conversations.mjs`。必要に応じて会話品質専用の検証スクリプト・入力ケースを追加する。

- 通常テスト: ゲームの段階・出題と回答・結果・再開、冒頭の重複防止、60往復の上限、候補生成失敗時、重複送信・古いrevision・言語変更の競合を検証する。
- 実LLM確認: 監査の「緊張」「仕事の失敗」「辛いチャイ」「静かにしたい」「遊びを始めて」「未設定の映画」を両者・両言語で再実行する。
- 合格文との完全一致ではなく、話し手・希望・時系列・依頼への応答を判定する。自動検査と人が読むログを併用する。
- 生成は揺れるため複数回確認し、観測した失敗数と試行数を記録する。少数例の成功を品質保証と扱わない。
- 相性分析についても、プレイヤー候補の視点誤りがなくなった履歴を使って引用・解釈を確認する。場面の行動結果から性格を決めつける仕様にはしない。

## コミットの区切り

1. 返答候補の視点・整合性と相手の応答改善（1・2と関連検証）。
2. 場面遷移・香り当ての実際のプレイ（3と関連検証）。
3. 冒頭の履歴統合と人物ごとの反応（4・5と関連検証）。
4. 言語変更時の候補と総合的な再シミュレーション（6・7）。

各区切りで検証してpushする。生成処理を分けることで増える待ち時間・API呼び出し数も記録し、会話品質と合わせて確認する。
