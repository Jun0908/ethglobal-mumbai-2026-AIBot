# 会話と相性の実装仕様案

2026-11-06。既存コードに基づく実装計画。機能実装は未着手。
体験の目的は `CONVERSATION_MATCHING_PLAN.md` に記載。本書はデータ・状態・API・実装順を定義する。

## 1. 最初に作る範囲

雨の日のストーリーを再利用し、「会話 → 行動 → 反応 → さらに会話 → 振り返り」を成立させる。新しい舞台やシナリオの大量追加は、この体験を確認してから行う。

最初の完成条件は、Ashaと会話し、Miraにも会い、Ashaの続きへ戻れ、両方の会話から共通点・違い・未確認点を見られること。自分のAI作成は任意のまま。

既存の `mode: rain` とモード省略時のAPIを保ち、新UIは `mode: rain-dialogue` を使う。状態と公開DTOはモード別の判別可能な型にする。移行中も既存テストが意味を失わないようにする。

## 2. 画面と操作を固定する

### 相手一覧

- Asha / Miraのカードに「未会話」「会話中」「振り返りあり」を表示する。
- 未会話なら「話してみる」、既存セッションがあれば「続きから話す」。新規開始は別操作にする。
- 未会話の相手に推薦順位や相性ラベルを付けない。「性格の違う2人と話せる体験版」と説明する。
- メインボタンをAshaへの直行から「相手を選ぶ」にする。

### 会話画面

- 会話履歴を常時表示し、相手の最新発言の下に短い返答候補を3つと「その他・自分で書く」を配置する。その他を選ぶと同じ返信領域が入力欄に切り替わる。送信できる入力領域は1つだけ。
- 候補はユーザーの発言として送信する。親しみを示す、別の希望を伝える、理由を聞く等の異なる方向を用意し、すべてが同意や迎合にならないようにする。
- 行動は別の「次の展開」領域に表示する。現在の雨の3段階と選択肢を再利用する。
- 会話を2往復したら次の展開を控えめに案内する。未達でも進められ、達成しても自動で場面を移動しない。この回数は体験調整の初期値で、相性判定の信頼度を意味しない。
- 行動を選んだ後も会話領域を保つ。「振り返る」は常時使え、終了時は「まだ話す」「相手一覧へ」を表示する。
- デスクトップでもスマートフォンでも会話を先に読める順序にする。返答候補と行動の見た目・見出し・読み上げ名を区別する。

### 振り返りと比較

- 4観点、会話の引用、AIの見立て、未確認点を表示する。引用を押すとその発言へ移動する。
- 「自然体で話せたか」「また話したいか」は任意回答。本人の感想はAIの見立てとは別欄に置く。
- 両者を同じ4観点で比較する。未会話や発言不足を低評価に変換しない。総合得点・自動順位は初期版に入れない。
- 矛盾する証拠があれば併記する。本人が「この解釈は違う」と指摘した項目は非表示または訂正待ちにし、元の発言を改変しない。

## 3. サーバー状態の分離

新モードでは `story.node === ending` は物語の完了だけを表す。会話を拒否する条件に使わない。

| 操作 | 物語 | 会話 | 振り返り |
| --- | --- | --- | --- |
| 返答を送る | 変更なし | 発言・反応を追加 | 前版は残し、更新可能と表示 |
| 行動を選ぶ | 1段階進む | 行動と反応を追加 | 更新可能 |
| 最後の行動 | ending | 引き続き送信可能 | 作成可能 |
| 振り返りを開く | 変更なし | 閉じない | スナップショットで生成 |
| 相手一覧へ戻る | 変更なし | サーバーに保持 | 保持 |
| 続きから話す | 保持 | 同じセッションを取得 | 保持 |
| 新しく遊ぶ | 初期状態 | 新しいID、旧会話を上書きしない | 旧結果を保持 |
| 期限切れ・同意撤回 | 操作不可 | 操作不可 | 新規生成・取得も権限確認 |

`story.revision` は行動の競合検知に維持する。別に `conversationRevision` を持ち、発言・候補の更新と分析の世代管理に使う。会話中に進捗率が後退したり、古い分析が最新として出たりすることを防ぐ。

新モードの申請ボタンは物語完了後に有効にする。会話を続けても申請済み状態は消さない。振り返りは完了前でも使える。物語完了と実際の相手の同意は別扱い。

## 4. 必要なデータ

### メッセージ

`id`, `role`, `text`, `kind`, `locale`, `sceneNode`, `sequence` を保持する。

`kind` は `free_text`, `suggested_reply`, `story_action`, `agent_reply`。返答候補を選んだことは本人のその場の表現として扱うが、自発的な価値観の申告と同一視しない。場面移動の選択だけで恒常的な性格を断定しない。

### セッション

既存の所有者・相手Persona・同意バージョン・matchIdに加え、安定した相手参照、モード、作成日時、最終活動日時、会話revision、返答候補セットを保持する。デモの相手参照は `demo-calm` / `demo-playful` で、毎回作成されるCapsule UUIDから人物名を推測しない。

### 分析結果

`gameId`, `conversationRevision`, `locale`, `analysisVersion`, `generatedAt`, `dimensions[]` を保持する。

各観点は `dimension`, `observation`, `evidenceRefs[]`, `interpretation`, `unknowns[]`。`observation` は `aligned`, `different`, `adapted`, `mixed`, `unknown`。一つの場面の証拠なら「今回のこの場面では」と範囲を限定する。

引用参照は `messageId` と原文内の開始・終了位置。画面に出す引用はサーバーが元メッセージから切り出す。モデルが返した引用文字列をそのまま信用しない。

## 5. LLMの仕事とアプリの仕事

### 会話生成

LLMには相手の承認済みPersona、現在の場面、会話履歴、公開済みの事実を渡す。1回の生成で台詞・表情・次の返答候補を返し、候補用の追加呼び出しを毎回増やさない。構造と長さを検証する。

自然な相互会話を優先し、質問だけを連続させない。相手自身の好みや具体的な反応を話す。場面移動はサーバーだけが行う。ユーザーの入力文をゲーム状態の命令として実行しない。

候補だけが不正なら、台詞が有効な場合は返答と自由入力を表示する。台詞生成に失敗したら会話状態を進めず、未送信文と再試行手段を保持する。生成された候補セットにIDとrevisionを付け、押された候補はサーバーがそのセットから解決する。

### 相性の振り返り

返答ごとには分析しない。ユーザーが振り返りを開くか「更新」を選んだ時点で生成し、同じrevision・言語・分析versionの結果は再利用する。

分析モデルへの入力は閲覧可能な会話のみ。非公開Personaを丸ごと渡さない。会話前の自己Persona比較は別機能として後段に分け、会話由来の見立てと混ぜない。

処理順序：会話スナップショット取得 → LLMによる観点と証拠候補の抽出 → サーバー検証 → 結果保存。

- 参照がそのセッションに属し、存在し、引用位置が正しいことを確認する。
- 「合う」には双方の関連発言、「違い」には対立する希望、「歩み寄り」には違い・代案・双方の反応という時間順の証拠を要求する。
- 役割・種別・順序の構造条件を満たさない観点はunknownへ落とす。外部から送られた既成スコアを受け取らない。
- 構造が正しいことは意味解釈が正しい保証にはならない。解釈は「AIの見立て」と表示し、原文確認・訂正の導線を維持する。根拠不足を推測で埋めない。
- 分析失敗は「分析できませんでした」と再試行を表示し、会話を止めない。「情報不足」とシステムエラーを混同しない。

分析中に会話が進んでも、そのスナップショットの結果として保存する。古い結果が新しい結果を上書きしない。保存直前に所有権と利用同意を再確認する。

## 6. APIの追加・変更

| API案 | 目的 |
| --- | --- |
| `POST game/start` | 新モードで開始。意図した新規開始と再開を混ぜない |
| `GET games` | 所有者のセッション概要。期限内かつ利用可能なものだけ |
| `GET game/{id}` | 所有権と同意を確認して会話を復元 |
| `POST game/message` | 自由入力または候補ID、revision、clientTurnIdを受ける |
| `POST game/action` | 行動IDとstory revisionで既存分岐を進める |
| `POST game/reflection` | 指定セッションの会話スナップショットを分析 |
| `POST game/feedback` | 本人の任意感想と見立ての訂正状態を保存 |

`clientTurnId`は送信単位のUUID。同じID・同じ内容の再送は保存済み結果を返し、内容が異なる再利用は拒否する。二重クリック、送信後の通信切断、LLM応答後の再試行でも会話や料金が不必要に増えないようにする。ただしプロセス停止時の厳密な外部API呼び出し重複防止はメモリ実装だけでは保証できない。

## 7. 会話の記憶と保存の境界

現在は会話もログイン状態もプロセス内Mapで、会話の期限は開始から2時間。ブラウザーのlocalStorageに会話本文を保存して解決しない。

初期版は「同じログインセッション内で再開・比較」に範囲を定める。会話の有効期限は活動に合わせて延長するが、認証の有効期限を超えない。ページ更新後もサーバーから復元できる。サーバー再起動・認証期限切れ後の復元は保証しないことを明記する。

翌日以降の再開を提供する段階では、永続的な本人識別、暗号化された会話・振り返りの保存、保持期間・削除をまとめて実装する。会話ファイルだけ保存してログインとの対応を失う中途半端な永続化は避ける。

長い会話は直近の発言と根拠ID付きの要約を生成時の文脈に使う。元の会話は期限内保持し、引用の参照元にする。要約は新しい事実の証拠にはしない。矛盾や後の訂正を保持する。上限に達した場合は会話を黙って忘れるのではなく区切りを案内する。

## 8. 実装単位と確認

| コミット単位 | 主な変更箇所 | 確認すること |
| --- | --- | --- |
| 1. 会話データと再開 | `game.ts`, `store.ts`, API, 新モード用schemas | 終了後の会話、相手別復元、期限・所有権、旧モード互換 |
| 2. 会話中心の画面 | `masala-app.tsx`, `rain-game.tsx`の新モード用コンポーネント, CSS, i18n | 返答と行動が区別できる、その他入力、スマホ、入力保持 |
| 3. 返答と候補生成 | `llm.ts`, schemas, 文脈構築 | JA/EN、性格差、迎合しすぎない会話、記憶、重複送信 |
| 4. 根拠付き振り返り | 新規`reflection.ts`, `server/reflection.ts`, API, 表示コンポーネント | 偽引用・別セッション参照拒否、unknown、競合・失敗の分離 |
| 5. 相手比較と本人の感想 | セッション一覧、比較コンポーネント、API | 未会話を低評価にしない、根拠への移動、自己感想とAI解釈の分離 |

各単位で必要な型チェック・テストを行い、意味のある区切りでcommit / pushする。最後に本番ビルドとブラウザーの通し操作を行う。

LLM品質は固定の例で比較する：好みが一致、好みが違うが調整できる、一方だけが合わせる、話題不足、冗談、後からの訂正、判定を操作する入力。文字列の完全一致を合格条件にせず、根拠の存在・解釈の妥当性・相手らしさを確認する。

既存の人物イラストの差別化と新しいデート場面は、この5単位の体験確認後の改善として扱う。先に会話と相性説明が成立することを確認する。
